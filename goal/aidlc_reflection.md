# 🧠 AIDLC 实践反思与非技术维度分析

> 本文件基于项目真实开发历程编写，所有论据均来自实际代码审计和开发记录  
> 创建时间：2026-07-30

---

## 一、AI 带来的组织变革（AI-Driven Organizational Change）

### 1.1 角色重构：从"写代码"到"审代码"

传统开发模式中，开发者的核心工作是**写代码**。AI 辅助开发后，角色的核心变成了**审代码**和**做决策**。

本项目中的真实案例：

| 阶段 | 传统模式 | AI 辅助模式 | 角色变化 |
|------|---------|------------|---------|
| 需求分析 | 产品经理逐条写需求 | AI 生成 24 条 FR + 22 条 US，人工逐条确认 | 从"写"到"审" |
| 设计 | 架构师画图设计 | AI 生成 ADR + 6 份设计文档，人工审阅 | 从"画"到"判" |
| 技术选型 | 开发者调研选型 | AI 提出 4 种方案，人工决策 | 从"选"到"决" |
| 实现 | 逐行写代码 | AI 生成代码框架，人工修正 | 从"写"到"修" |

**关键洞察**：AI 没有取代人，而是把人的工作重心从"执行"上移到了"判断"上。

### 1.2 组织效率的变化：加速但非线性

从实际开发节奏看：

```
需求阶段: 30 分钟完成 24 条需求 + 22 条用户故事（传统约 2-3 天）
设计阶段: 30 分钟完成 6 份设计文档 + 6 个 ADR（传统约 1-2 天）
实现阶段: 约 4 小时完成 25 个任务（传统约 3-5 天）
验证阶段: 30 分钟端到端测试 → 发现 bug → 修复 → 迭代
```

**但"快"不等于"好"**，实际遇到的三个典型问题：

**问题 1：AI 生成的内容需要人工核验才能用**
> history.md 第 293 行：`db = SQLAlchemy()` 循环依赖问题
> AI 初始生成的代码将 `db` 定义在 `app.py` 中，导致 Flask debug reloader 重启时报错。这个架构问题需要在集成阶段才发现修复。

**问题 2：AI 降级逻辑可能被忽略**
> `ai_copy_service.py` 中定义了 `_fallback_generate()` 但从未被调用。AI 生成代码时"看起来完整"，实际上降级路径是断的。传统开发中，AI 文案失败应该降级到模板——这个逻辑是人工审计才发现的。

**问题 3：文档跟不上代码变更**
> 追踪矩阵路径仍指向 TypeScript（`lib/services/auth.ts`），但实际代码已迁移到 Flask/Python。AI 生成文档后，代码变更时文档容易被遗忘。

### 1.3 管理上的启示

**AI 时代的管理者需要关注三个新维度：**

| 传统管理 | AI 时代管理 | 本项目的经验 |
|---------|------------|------------|
| 管进度 | 管**质量** | AI 生成太快，质量把关变成瓶颈 |
| 管人 | 管**人+AI 协作** | 人和 AI 的接口（AI 输出→人确认→人修正）需要明确 |
| 管输出 | 管**认知** | AI 做了 80%，但剩余 20% 的判断力才是价值所在 |

## 二、AI 反射管理（你要避免成为"AI 的传声筒"）

### 2.1 核心问题：当你不了解 AI 做了什么事

> 评委可能会问的一个关键问题：  
> **"AI 帮你生成了代码，你自己还理解这段代码吗？如果 AI 出错了，你能发现吗？"**

这是"AI 反射"（AI Reflection）问题——当人过度依赖 AI，失去对工作内容的直接理解，变成"AI 的传声筒"。

### 2.2 本项目中的实际反射案例

**案例 1：技术栈迁移——人做了关键决策**

```
AI 方案：Next.js + Prisma + TypeScript
实际情况：npm install 一直超时
人的决策：果断迁移到 Flask + SQLAlchemy
结果：迁移后 30 分钟跑通全流程
```

这里的**反射**：如果只是让 AI 继续尝试安装依赖，可能浪费数小时。人的判断（"这条路径走不通，换一条"）是整个项目的转折点。**这个决策 AI 做不了**——因为 AI 不会主动说"换个技术栈吧"，它只会继续试。

**案例 2：循环依赖 bug——AI 生成的隐患**

```
AI 生成代码：将 db 定义在 app.py → models 从 app import db
问题：Flask reloader 重启时报错
修复：提取 extensions.py 独立文件
修改涉及：11 个 model 文件 + 8 个 service 文件
```

这里的**反射**：AI 生成的代码"能用"但"不够好"。如果不理解 Flask 的扩展初始化机制，开发者可能看不出这个隐患。只有当触发 reloader 时才会暴露。

**案例 3：AI 降级未接通的隐性 bug**

```
位置：ai_copy_service.py
现象：_fallback_generate() 定义了但从未被调用
后果：AI 失败时返回空文案，而不是预设模板
发现方式：代码审计（不是运行时报错）
```

这里的**反射**：这是最典型的问题——AI 写了两个函数（`_ai_generate` 和 `_fallback_generate`），看起来"降级设计完整"，但**调用路径没连上**。表面检查看不出问题，只有深入跟踪代码执行路径才能发现。

### 2.3 如何确保 AI 做的事你了解——四层防御

| 层次 | 方法 | 本项目实践 |
|------|------|-----------|
| **L1：审查输出** | AI 生成的所有代码，人都必须读一遍 | 发现 ai_copy_service 降级 bug |
| **L2：验证行为** | 跑测试、模拟异常路径 | 端到端 10 步验证覆盖正常流程 |
| **L3：理解架构** | 不看 AI 生成的代码，自己先画架构图 | ADR 记录帮助理解设计决策 |
| **L4：复盘反思** | 结束后回顾"AI 做了什么，人做了什么" | 本文件 |

### 2.4 一个实用的判断标准

**如果你不能用自然语言向另一个人解释一段 AI 生成的代码做了什么，那你也不应该把它放进项目。**

本项目中的反例：
> ai_copy_service 的降级逻辑——人类开发者以为"降级已经实现了"，但实际上没有。因为**没有人真正跟踪过调用路径**。

本项目的正例：
> 原子库存扣减的 SQL——开发者理解每一行 SQL 的含义，知道为什么需要 `remaining_stock > 0` 条件，知道为什么用 `text()` 执行原生 SQL。

## 三、AIDLC 实践的真实问题与反思

### 3.1 AIDLC 在本项目中到底怎么运转的

```
需求 ──→ 设计 ──→ 规划 ──→ 实现 ──→ 验证
 │        │        │        │        │
 Q&A×11  ADR×6   25任务   4段完成   10步端到端
 30min    30min   15min    ~4h      30min
```

### 3.2 实际遇到的 5 个关键问题

#### 问题 1：技术栈规划在实现阶段被推翻

**AIDLC 设计阶段**的技术决策：Next.js + Prisma + SQLite  
**实现第 1 步时**发现：npm install 一直超时，Node.js 环境不可用

**根源分析**：
- 设计阶段假设"开发环境一定可用"——这个假设在竞赛环境下不成立
- AIDLC 各阶段之间的门禁检查只检查"文档完整性"，不检查"环境可行性"

**优化建议**：
- 阶段 1（需求）结束后，增加**环境可行性验证**步骤：先跑通 `pip install` 或 `npm install`，再进入设计阶段
- ADR 应该增加"环境依赖"字段，标注该决策对外部环境的要求

#### 问题 2：AI 生成的设计文档与实际代码脱节

设计文档（`traceability-matrix.md`）中写的路径是：
```
lib/services/auth.ts (TypeScript)
```

实际代码路径是：
```
services/auth_service.py (Python)
```

**根源分析**：
- 设计阶段用 AI 生成的设计文档是"理想化"的（假设 Next.js 路径）
- 实现阶段迁移了技术栈，但没有人回去更新设计文档
- AIDLC 没有"设计文档同步"的回溯机制

**优化建议**：
- 技术栈发生变更时，应自动触发"设计文档同步"任务
- 追踪矩阵每个阶段都要更新，不是一次性交付物

#### 问题 3：25 个任务的状态跟踪粒度不够

任务列表只有"完成/未完成"，缺乏：
- 每个任务的实际耗时（方便下次估算）
- 遇到的问题记录（经验积累）
- 代码 Review 状态

**根源分析**：
- AI 生成的任务模板只有复选框和验收标准
- 竞速开发模式下，没有时间记录"踩坑日志"

**优化建议**：
- 每个任务增加"实际工时"字段
- 增加"阻塞原因"记录
- 任务状态增加"review"状态，不直接从进行中跳到完成

#### 问题 4：前端页面完成度不均

后端 API 全部完成（30+ 端点），但前端有多个页面是"开发中"占位符。

**根源分析**：
- 没有按"垂直切片"（一个功能前后端都做完）来规划任务
- 任务是按"层"分的（T-XXX 后端 → T-XXX 前端），导致后端全部做完后才发现前端来不及

**优化建议**：
- 任务应该按**功能**切割，不是按**技术层**切割
  - ❌ 先做所有后端的 API，再做所有前端的页面
  - ✅ 做完"活动管理"的前后端，再做"领券"的前后端
- 每个功能完成后再进入下一个，演示时至少有一个完整的闭环

#### 问题 5：AI 降级的"看上去很美"

4 个 AI 服务（推荐、风控、文案、画像）都有降级设计，但实际只有 3 个生效。文案降级的 `_fallback_generate` 函数从未被调用。

**根源分析**：
- AI 生成代码时，倾向于"生成看起来完整的代码"
- `_fallback_generate` 存在→看起来"降级已实现"→人没有深究
- 这是 AI 反射问题在 AIDLC 中的具体体现

### 3.3 如果重来会做的 3 个改变

**1. 先验证环境，再设计架构**

```
当前流程：需求 → 设计 → 规划 → 实现
优化流程：需求 → 环境验证 → 设计 → 规划 → 实现 → 设计同步
                              ↑
                        先跑通 npm install / pip install
                        确认 AI API 可用
                        再确定技术栈
```

**2. 按功能切分任务，而不是按技术层**

```
❌ 当前方式：
  T-004 后端活动管理 API
  T-005 后端领券 API
  ...
  T-012 前端活动管理页面
  
✅ 建议方式：
  Sprint 1: 活动管理（后端 API + 前端页面 + 验证）
  Sprint 2: 领券（后端 API + 前端页面 + 验证）
  Sprint 3: 核销（后端 API + 前端页面 + 验证）
```

**3. 每个 AI 功能强制人工验证降级路径**

```
AI 功能验收时增加必查项：
□ AI 正常时功能可用
□ AI 失败时触发降级
□ 降级输出在页面上可读
□ 降级路径的代码调用路径已跟踪
```

## 四、竞赛话术建议

### 4.1 应对"AI 帮你做了，你做了什么"问题

> **不要这样说**："AI 生成了所有代码，我们只是审核了一下。"
>
> **建议这样说**：
> "AI 生成了 80% 的代码框架，但我们做了 3 个关键决策：
> 1. **技术栈迁移**——当 Node.js 环境不可行时，我们在 30 分钟内决策迁移到 Flask，避免了数小时的徒劳尝试
> 2. **架构修复**——AI 生成的扩展注册方式有循环依赖风险，我们在集成测试中发现并重构了整个扩展模块
> 3. **降级验证**——我们发现 AI 生成的降级代码有一条路径是断的（文案生成），修复后才真正实现了 4 个 AI 功能的完整降级
> 
> AI 加速了执行，但判断力来自人。"

### 4.2 应对"AI 代码你理解吗"问题

> **建议这样说**：
> "我们对每段 AI 生成的代码都做了人工审查和测试验证。
> 一个具体的例子是库存扣减——AI 建议用 ORM 的方式更新库存，但我们将它改为了原子 SQL UPDATE。
> 因为我们理解 SQLite 的锁机制，知道在这个场景下原子操作比 ORM 更可靠。
> AI 可以帮我们写代码，但**架构决策和对技术的深入理解**仍然来自团队的经验。"

### 4.3 应对"AIDLC 的价值是什么"问题

> **建议这样说**：
> "AIDLC 最大的价值不是流程本身，而是它创造了一个**人机协作的节奏**。
> 每个阶段的门禁检查让我们停下来思考：'这个结果真的对吗？'
> 这个停顿点正是人发挥判断力的地方——AI 快速产出，人审慎决策。
> 
> 我们实际验证了这个节奏的效果：
> - 需求阶段：AI 产出 24 条需求，人通过 11 轮问答确认了 6 个关键细节
> - 设计阶段：AI 产出 6 个 ADR，人在实现阶段推翻了一个（技术栈迁移）
> - 实现阶段：AI 产出了代码，人在验证阶段发现了降级路径的 bug
> 
> 没有 AIDLC 的门禁，这些问题可能会被跳过。"

## 五、评委隐性评分维度总结

### 5.1 评委可能观察的非技术点

| 维度 | 评委想知道 | 本项目可展示的证据 |
|------|-----------|------------------|
| **AI 与人的分工** | AI 做了什么，人做了什么 | 技术栈迁移决策、循环依赖修复、降级 bug 发现 |
| **风险意识** | 有没有考虑 AI 不可用 | 4 个 AI 服务 3 个有真实降级、原子库存扣减、幂等核销 |
| **工程化思维** | 有没有系统性的方法论 | AIDLC 全流程文档、追踪矩阵、门禁检查 |
| **反思能力** | 能不能识别自己的不足 | 本反思文档、已识别的前端页面缺陷、文档过时问题 |
| **沟通能力** | 能不能清晰表达项目价值 | 演示脚本、价值主张"AI 重构优惠券运营效率" |

### 5.2 最容易丢分的非技术坑

| 坑 | 为什么扣分 | 怎么避免 |
|----|----------|---------|
| 全是 AI 做的，团队没有贡献感 | 评委觉得"这项目换个团队也能做" | 突出人的决策和判断（见 4.1） |
| 技术很炫但不知道解决什么问题 | 评委觉得"为了 AI 而 AI" | 提前说明业务痛点（传统核销效率低、风控靠人工） |
| 演示很流畅但说不清原理 | 评委一问就卡壳 | 准备 3 个"为什么"的回答（见 4.2） |
| 文档完美但和代码不一致 | 评委发现一眼假 | 确保文档和代码一致（即使文档不完美） |
| 只说成功不说失败 | 显得缺乏深度 | 主动分享遇到的 bug 和怎么解决的（见 3.2） |

## 六、AIDLC 优化建议清单

### 对 AIDLC 方法论本身的改进建议

| 发现的问题 | 建议改进 | 优先级 |
|-----------|---------|--------|
| 设计阶段未验证环境可行性 | 门禁检查增加"环境验证"步骤 | P0 |
| 追踪矩阵没有回溯机制 | 技术栈变更时自动标记"需同步文档" | P0 |
| 任务按层不按功能切割 | 改为垂直切片（一个功能前后端完成再切下一个） | P1 |
| AI 降级路径无强制验证 | 验收标准增加降级路径跟踪 | P1 |
| 缺乏实际工时记录 | 任务模板增加"实际耗时"字段 | P2 |
| 阶段之间缺少回顾 | 每个阶段结束后增加 5 分钟快速回顾 | P2 |
