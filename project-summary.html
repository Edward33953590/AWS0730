这 22 小时实际发生了什么

AIDLC 四个阶段，每个阶段都有真实的故事

Phase 1 需求 30 分钟

AI 生成 24 条需求，人确认了 6 处关键调整，确定了 4 角色 + 7 券型的范围。这时候看起来很顺利。

Phase 2 设计 30 分钟 → 出问题了

AI 选了 Next.js + Prisma + TypeScript，ADR 都写好了。进到 Phase 3 第一步 npm install 一直超时。Node.js 环境不可用。

人的决定：30 分钟内全栈迁移到 Flask。设计文档作废，但项目活下来了。AI 不会主动说"换个方案吧"——这个决策只能人来做。

Phase 3 实现 AI 写的代码，人修的 3 个坑

AI 生成服务层、路由、模板，速度很快。但代码审核发现了三个问题：

① 循环依赖 — AI 把 db 定义在 app.py，models 从 app 导入。运行时报错。人把 db 抽到了独立的 extensions.py。
② 降级断路径 — AI 文案服务定义了 _fallback_generate() 但从未被调用。表面看"降级已实现"，实际调用路径没连上。
③ 竞态条件 — 双请求同时核销同一券码，ORM 检查都通过。线上查日志才发现。人加了 try/except IntegrityError 兜底。
Phase 4 验证 16 项测试 + 10 步手动验证

自动化测试覆盖全部 API，端到端手动验证覆盖 7 个移动端场景。手机扫码→自动核销→振动反馈，全程 2 秒。

测试环境：Windows 11 + Chrome + 手机 WiFi 局域网

降级路径代码审计AI 盲区

端到端场景验证不能省略

AI 写代码效率高，但 AI 生成的代码"能运行"不代表"正确"。降级没有调用路径、循环依赖只在运行时暴露——这些只有人能发现。

从代码中得出的反思

三个真实问题，三个改变

不是理论推演，是从实际报错和日志里发现的

问题 1 设计假设在实现时被推翻

Next.js 方案在文档里看起来很完美，但 npm install 一直超时。设计阶段没有验证"环境是否可用"这个前提。

→ 下次补充"环境验证"步骤再进入设计
问题 2 任务按"层"分，而不是按"功能"分

先做完全部后端 API（30+ 端点），再做前端页面。导致演示时后端完整但多个页面是占位符。

→ 按"功能"垂直切片：活动管理（前后端）→ 领券 → 核销
问题 3 AI 降级路径没有强制验证

文案服务定义了 _fallback_generate() 但入口 never 走到那里。人以为"有降级"，实际上是断的。验收时如果只测"AI 正常"这条路，永远发现不了。

→ 验收清单增加必查项：AI 异常时是否触发降级 + 降级输出是否可读

这三个问题有一个共同点：表面看起来一切正常，但代码执行路径是断的。AI 擅长让表面完美，人需要穿透表面。
